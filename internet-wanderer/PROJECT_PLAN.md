## 1. 产品理解与需要修正的假设

### 1.1 它是什么

Internet Wanderer 是一个让人短暂离开熟悉信息环境的探索空间。用户无需说明想找什么，只要决定“继续走”，就能遇见一个独立网站、一则陌生新闻，或一段过去的互联网。

核心体验由三部分组成：

- **低决策成本：**一键出发，结果出现后只需决定打开、略过或继续。
- **可感知的陌生：**内容来源、年代、语言或形式发生变化，而不只是同一类链接换一个地址。
- **有上下文的偶遇：**一两句说明帮助用户理解为什么值得看，又不会提前讲完全部惊喜。

它不承担搜索引擎的查准率、新闻客户端的全面及时、书签工具的组织能力，也不承诺重建完整的历史互联网。与普通随机网址按钮的差异是：**有人工筛选、有来源说明、有时间语境，并且能持续漫游。**

### 1.2 需要直接指出的问题

| 原始想法中的张力 | 产品影响 | V0.1 的处理 |
| --- | --- | --- |
| 随机不等于惊喜 | 完全随机可能只是垃圾、重复或打不开的页面 | 在精选池内随机，近期去重，限制同一域名连续出现 |
| “你从没见过”需要了解用户 | 没有用户画像就无法保证陌生程度 | 文案表达探索邀请，不宣称已经测量用户的信息圈 |
| 三个模块都自动化会放大开发量 | 新闻与档案接口可能消耗掉全部时间 | 网站与历史内容人工维护，只有少量 RSS 做轻量更新 |
| 一个年份不等于某一天 | “2007 年内容”容易被误展示为“2007-06-29 当天发生” | 第一版按年组织；只有有证据的事件显示具体日期，不设 TODAY 栏目 |
| Wayback 有记录不等于能完整体验 | 图片、脚本、登录和子链接可能缺失或跨年 | 人工检查选定快照，明确显示抓取时间与原网址，跳转外部查看 |
| “全球新闻”可能实际只有少数英语媒体 | 地理标签制造了虚假的多样性 | 展示媒体所在地区与原文语言，明确样本覆盖，不声称全球代表性 |
| 内容太少会很快耗尽 | 工程完成后仍可能不好玩 | 把内容筛选作为开发任务，先保证每条值得点开，再扩大数量 |

建议保留英文模式名与标语，V0.1 的解释文案使用中文；外部内容保留原文并标注语言。暂不建立界面多语言系统和自动翻译链路。

### 1.3 怎样判断第一版成立

先用体验验收，不建设分析平台：作者与 3～5 位朋友各玩约 10 分钟，记录“愿意打开哪些内容、什么时候想退出、是否找得到上一站”。重点观察是否有人在没有任务的情况下自愿再点几次。

发布时应满足：连续体验 20 次不因内容池或接口错误卡死；有足够候选时不在最近 20 条中重复；外站返回后还能继续；至少有几条内容让测试者愿意保存或分享。最后一项是需要体验验证的产品目标，不是由代码测试替代的指标。

## 3. 最少页面与路由

只需要 **3 个页面级视图**。静态托管优先采用 HashRouter，避免 GitHub Pages 刷新深层路径时返回 404；部署到仓库子路径时配置 Vite 的 `base`。

| 页面 | 示例地址 | 内容 |
| --- | --- | --- |
| Home | `/#/` | 标语、最明显的 Surprise Me、三个模式入口、简短说明 |
| Wander | `/#/wander?mode=elsewhere` | 当前模式、内容卡、下一站、打开原站、最近遇见抽屉 |
| About | `/#/about` | 产品意图、来源与更新方式、内容范围、反馈方式 |

News Drift、Time Machine、Surprise Me 都是 Wander 的模式：`mode=news`、`mode=time&year=2007`、`mode=surprise`。不存在四套相似结果页；也不单设 Wander Result、History 或收藏页面。

Time Machine 进入后显示支持年份与“随机年份”。只有这一模式出现年份控制。History 用结果页内的抽屉或折叠区承载，About 不进入主要操作路径。

## 4. 核心用户流程与随机规则

### 4.1 一次漫游

1. 打开 Home，点击 Surprise Me，或者选择一个模式。
2. 系统从已加载的本地内容池选出目标，显示短暂的过渡与内容卡。
3. 卡片显示标题、简短介绍、域名／来源、类型；新闻显示发表时间，历史内容显示关联年份与必要的日期说明。
4. 用户点击“打开这一站”，由明确的链接点击在新标签页打开外站；漫游器保留原标签页。使用 `rel="noopener noreferrer"`。
5. 用户回到原标签页，点击“下一站”，或从最近遇见中重新打开上一条内容。

不在抽取完成后自动打开新窗口：异步弹窗容易被拦截，也会让用户失去方向。外站不嵌入 iframe；很多网站限制嵌入，历史站点也未必能在 iframe 中正常工作。

“返回”分开处理：站内“上一站”恢复刚才的卡片；外站在新标签页打开后，返回原标签页继续。浏览器刷新恢复当前结果和模式，浏览器后退仍遵守正常路由行为。

### 4.2 三个模式的最小差异

- **Elsewhere：**一次一张网站卡；人工写一句“你可能会在这里遇到什么”。不把页面做成网址目录，不必加入分类筛选。
- **News Drift：**一次一条新闻；显示媒体、媒体地区、原文语言和发表时间。媒体地区不等于事件发生地。不能识别可靠发表时间的 RSS 条目不进入新闻池。
- **Time Machine：**选择或随机一个支持年份，得到三张小卡组成的“年份包”：一件事、一个代表性去处、一张旧网页。点击任一张可打开；“再逛这个年份”换一组，“换个年份”进入另一个内容包。每年 6 条尽量覆盖这三个槽位；缺项时显示现有内容，不伪造填满。

Surprise Me 抽到历史内容时，先展示一张主卡和年份提示；用户可进入该年份的三卡内容包。这样主页的一次点击仍然只要求用户理解一个主要结果。

### 4.3 随机选择算法

第一版使用浏览器普通伪随机数即可，不需要推荐系统或随机服务。

1. **先确定合格候选。**过滤禁用、无合法 URL、过期新闻和不属于当前年份的条目。
2. **Surprise Me 先选池，再选内容。**Elsewhere / News / Time 三个有合格候选的池初始等概率；某池为空时重新归一化剩余池。避免网站池较大而淹没其他模式。
3. **池内做少量均衡。**网站优先避免与上一站同域名；新闻先等概率选有候选的媒体，再选条目；随机年份先等概率选支持年份，再选该年的内容。它们只是简单的分组抽样。
4. **近期去重。**最近 20 条按稳定 ID 去重；跨模式的同一条内容仍视为同一条。年份包中展示的三个 ID 也记入“最近遇见”。
5. **小池必须能继续。**候选耗尽时先放宽最旧的近期记录，再放宽同域名限制；仍保留年份、禁用状态和新闻时效这些硬约束。只有 1 条时允许重复并提示“这个角落暂时只有这一站”；0 条时显示明确空状态。

单模式没有内容时不悄悄跳到别的模式：给出“换个年份”“去 Elsewhere”或“Surprise Me”的按钮。Surprise Me 自身可以跳过空池，但所有池都为空时同样显示空状态。

这些权重与去重窗口放在一个小配置文件中。暂不加入 qualityScore、weirdnessScore、discoveryDistance：它们缺乏可一致维护的标注标准，容易产生没有意义的精确数字。

### 4.4 最近遇见、收藏与分享

- **V0.1 做本机最近遇见：**最多 20 条，保存内容 ID、遇见时间、模式与年份，并保存当前卡片 ID。再次打开时从当前数据解析；已下架条目显示“内容已移除”，不继续提供失效入口。
- 名称用“最近遇见”，不声称记录了用户在外部网站的实际访问、停留或阅读。
- localStorage 不可用、满额或损坏时降级为本次页面内存；它不应影响核心漫游。提供“清空足迹”。
- **收藏推迟到 V0.2。**第一版可用浏览器收藏或复制原站链接；不开发云收藏。
- 分享公开的主页链接即可。可稳定复现某条结果的站内分享链接另做，不让短期新闻失效问题拖慢 V0.1。

## 5. 统一数据模型

### 5.1 建议统一为 WanderItem

Website、News、Archive、Historical Event 共享稳定的基础字段，再带少量类型相关字段。**Old Website 不是第五种类型：**仍能访问的旧站是 `website`，主要通过历史快照访问的旧站是 `archive`。时间关联是内容的属性，不必把所有历史内容塞进单一类型。

以下是接口规划示意，不是本轮要实现的源码：

```ts
type WanderItem = {
  id: string;
  kind: "website" | "news" | "archive" | "event";
  title: string;
  url: string;
  sourceId: string;
  blurb?: string;
  language?: string;
  tags?: string[];
  enabled?: boolean;
  publishedAt?: string;
  history?: { year: number; occurredOn?: string };
  archive?: { originalUrl: string; capturedAt: string };
  evidenceUrls?: string[];
};
```

实现时用 Zod 做一次判别式校验，让下表约束生效；不让所有可选字段的组合都成为合法内容。

| 字段／规则 | 约定 |
| --- | --- |
| `id` | 人工内容使用稳定 slug；新闻优先用 `sourceId + guid` 派生 ID，无 GUID 时使用规范化原文 URL 的散列。不能使用数组下标或每次更新生成的随机 ID |
| `kind` | 决定内容语义与卡片展示。新增类型时扩展 renderer 与校验，不修改所有页面 |
| `url` | 用户实际打开的地址，只允许 HTTP(S)。Archive 使用经过检查的具体快照 URL；不在浏览器点击时临时猜测快照 |
| `sourceId` | 指向来源配置。采集来源、出版媒体及其展示规则集中管理，不把第三方原始对象传给组件 |
| `blurb` | 人工原创介绍或来源明确许可展示的摘要。缺省时只显示标题和来源；不是默认复制正文 |
| `language` / `tags` | 可缺省；不知道语言就标为未知，不根据域名推断。标签用于维护与轻量分组，暂不形成复杂用户筛选器 |
| `enabled` | 缺省为 true；人工审核后可下架。一个失效的实时网站可以禁用，另建经过验证的 archive 条目 |
| `publishedAt` | 新闻必填，使用带时区的标准时间；不以抓取时间冒充发表时间。异常未来日期进入待检查队列 |
| `history.year` | 表示人工确认的年份关联；进入 Time Machine 的条目必填。网站可表示“该年代表性去处”，不自动表示该年创建 |
| `history.occurredOn` | 仅对已核实的事件日期使用 `YYYY-MM-DD`；不知道具体日期就省略，不能补成 1 月 1 日 |
| `archive` | archive 类型必填；`capturedAt` 是真实抓取时间，`originalUrl` 是被存档地址；不能与事件日期、发表日期混用 |
| `evidenceUrls` | 历史事件必有至少一个可信参考链接；年份关联的依据也可记录在这里。尽量使用当时资料或机构一手说明 |

示例语义：一条“2007 年的互联网事件”可以同时具有 `history.year=2007` 与准确的 `occurredOn`；一张 2007 年网页快照的 `capturedAt` 只证明那时抓取到了页面，不证明页面内容当天发表。

### 5.2 数据文件与来源配置

- `data/sites.json`：人工精选的当前可访问网站。
- `data/history.json`：历史事件、代表性去处与选定快照，按 `history.year` 分组使用。
- `data/news.snapshot.json`：采集脚本生成并保留的最近成功新闻快照，包含每个来源的 `lastSuccessAt`。
- `config/sources.json`：来源 ID、名称、类型、URL／feedUrl、媒体地区、语言、展示政策、条款链接、核实日期、是否启用。
- `config/years.json`：支持年份、简短时代说明与主题键。增加一个年份主要是加数据和配置。

前三个内容文件使用 `{ schemaVersion: 1, items: [...] }` 外壳；新闻额外有 `sourceStates` 与 `generatedAt`。`generatedAt` 只表示文件生成，不替代每个来源的成功采集时间。前端所需的来源信息在构建时输出一个精简映射，内部采集配置不必全部发送给浏览器。

V0.1 不建独立 Category、Tag、Country、User、Bookmark 等关系表。来源地区是来源元数据；将来若需要事件发生地，再新增语义明确的字段，避免现在就把它与 `country` 混为一谈。

### 5.3 保持兼容的最小约定

稳定 ID、类型语义、日期语义和来源归属优先保持不变。新增可选字段兼容旧数据；新增必填字段或更改语义时提升 `schemaVersion` 并提供一次转换。不在每个条目中复制完整来源信息和版本号。

浏览器只保存少量 ID，尽量避免保存整个内容对象，从而降低数据更新后本机足迹陈旧的风险。已有网页打开后以本次加载的同一快照完成漫游，刷新才切换新快照，避免一次会话中内容突然变化。

## 6. 数据来源与第一版选择

详细比较、使用条件及验证清单见 [DATA_SOURCES.md](DATA_SOURCES.md)。这里给出项目决策。

| 内容 | V0.1 的来源与数量 | 不采用的做法 |
| --- | --- | --- |
| 现代陌生网站 | 手工精选至少 30 个；从个人博客、独立站目录、大学／实验室网页、数字艺术与小型档案中找候选，逐个检查 | 大规模抓取目录、直接复制别人整个列表、把随机域名当成发现 |
| 新闻 | 目标 3～5 个明确提供 RSS 且展示条件适用的来源；尽量覆盖 3 个媒体地区并包含非综合新闻来源；每源最多保留 15 条、只进入近 7 天内容 | 浏览器直接跨域读取 feed、每次点击调用新闻 API、为补足数量抓取全文 |
| 历史新闻 | 首版不提供通用历史新闻检索；用人工写的“当年事件”与来源链接形成历史语境 | 宣称能自动还原任意一天新闻，或把今天的回顾文章伪装为当年的报道 |
| 旧互联网 | 3 个精选年份，建议从 1999、2007、2012 中开始；每年至少 6 条、覆盖事件／去处／快照 | 没有内容却允许任意年份选择；承诺完整旧站体验 |
| Wayback / Internet Archive | 手动选定具体快照或馆藏页，存入 history.json；浏览器只跳转 | 点击关键路径依赖 Wayback 查询、嵌入整站、自动保存所有站点 |

年份是策展建议，尚未完成数据核验。某年无法找到可靠快照时可以换年；显示的年份集合必须由实际审核通过的数据决定。

### 6.1 RSS 快照的更新流程

```text
来源白名单 → 定时／手动采集 → adapter 归一化 → 校验与去重
                    ↓ 单个来源失败：保留该来源的最近成功结果
             news.snapshot.json → 构建静态站 → 发布

浏览器 → 本站静态数据 → 本地选取 → 展示卡片 → 用户点击原站
```

第一版只实现一个 RSS adapter，兼容实际选中的 RSS／Atom 格式；不设计通用爬虫框架。

- 计划每 12 小时更新一次，支持手动运行；不宣称实时新闻。
- 初版可在一个 GitHub Actions 工作流中完成采集、保存快照、构建与 Pages 发布。新闻快照保存在仓库，作为下一次运行的最近成功数据；不用缓存服务或数据库。
- 定时任务显式执行发布步骤，不依赖机器人提交再触发另一个工作流；避免触发链路失效或循环。发布串行执行，遇到提交冲突本轮停止并保留旧站点。
- 成功检查但没有新文章时也更新对应来源的 `lastSuccessAt`。单个来源失败不更新它的成功时间，也不清空其他来源。
- 请求设置有限超时与最多一次退避重试；仅请求配置中的 feed，按源限制数量，避免把采集变成爬虫。
- 将 HTML 转为纯文本，丢弃脚本和不合法链接，校验日期，按规范化 URL／GUID 去重；不把 RSS HTML 直接注入页面。
- 对于禁止再展示摘要的来源，只输出其允许的字段；无法明确适用条件的来源先禁用。

GitHub Actions 定时执行不应被视为准点保证；公共仓库的计划任务也可能因长期不活跃被停用，部署时复核当前官方规则。页面始终依据真实时间判断新鲜度，不依赖下一次部署一定按时发生。

### 6.2 失败与降级必须具体

| 情况 | 行为 |
| --- | --- |
| 一个 feed 失败 | 保留该源最近成功快照，其他来源照常更新 |
| 某源超过 48 小时未成功更新 | 显示上次更新时间；其条目退出 Surprise Me 的新闻候选，News Drift 中可明确作为旧快照查看 |
| 新闻发表时间超过 7 天 | 从 V0.1 新闻池隐藏，包括旧快照查看；不继续称为当前新闻 |
| 没有符合新鲜度条件的新闻 | Surprise Me 只在其他合格池中随机；News Drift 显示更新暂不可用，并提供其他模式入口 |
| 第一次采集全部失败且没有快照 | 不生成假新闻；其余模块仍可构建，News Drift 显示未就绪。这是受限预览，不是完整四入口 MVP 验收通过 |
| 选中的 Wayback 快照无法访问 | 提供原网址与“下一站”；维护时禁用或更换该条目。应用无法可靠检测外部标签页的加载结果 |
| 外站地址失效或转售 | 人工复核后下架；初版提供项目反馈入口，不自动把 HTTP 403 认定为永久死亡 |

如果找不到 3 个条款合适的 RSS 来源，可先用 1～2 个经过验证的来源做标明覆盖范围的预览，再补足；不为了凑数引入全文爬虫或未经授权的 API。若新闻集成超过约半天仍被访问或条款卡住，把它从首次可玩预览中延后，保住核心循环。

## 7. 技术方案比较与选择

| 方案 | 对这个项目的好处 | 成本与适用边界 | 结论 |
| --- | --- | --- | --- |
| **React + Vite + TypeScript** | 随机交互与本机状态直接；静态产物可迁移；数据与 UI 易拆分 | RSS 必须通过构建／采集脚本处理；默认不提供服务端 API | **V0.1 推荐** |
| Next.js | 后续需要服务端 API、账号、动态分享页时集中开发方便 | 当前功能用不到大部分服务端能力；静态导出与服务端能力存在边界 | 目前不引入；已熟悉 Next.js 也可做，但不为此增加后端 |
| Astro | About、年代文章和内容型站点很合适，可用 islands 承载交互 | 本项目多数核心界面共享连续交互与状态，最终可能仍是一个较大的 React island | 若未来变成“档案文章 + 少量漫游”再考虑 |
| 纯 HTML / CSS / JavaScript | 最少工具，极小原型很快 | 四入口、历史包、本机状态与失败处理增加后，手写 DOM 容易混杂逻辑 | 适合一页体验验证，不作为本次长期维护起点 |

### 7.1 最终推荐的最小组合

- React + Vite + TypeScript；React Router 的 HashRouter 承载三个页面。
- CSS 或 CSS Modules + CSS variables；不先引入大 UI 组件库。
- Zod 负责数据边界校验；一个成熟 RSS parser 负责实际选中 feed 的解析。
- 普通 React state / reducer 管理页面状态；不引入全局状态库。
- JSON 管内容，Git 管审核与版本；localStorage 管最近遇见。
- Node 脚本处理 RSS，GitHub Actions 负责周期更新与构建，GitHub Pages 作为默认静态发布目标。

部署步骤在实施时是：创建仓库 → 加入数据与源码 → 配置仓库子路径 → 构建校验 → 发布 `dist` → 开启定时更新 → 在公开链接验证移动端与外站返回流程。当前只规划，不创建仓库、不执行发布。

同一份 `dist` 也能迁移到其他静态托管。免费托管与 Actions 配额需要按当时账户及官方条款确认；目标是没有必需的付费 API、数据库或域名支出，不作永久零成本保证。

### 7.2 Supabase 与 SQLite 是否必要

**现在两者都不需要。**数据由作者维护，浏览器只读，没有多用户写入、跨设备同步或在线审核，数据库不能明显改善第一版体验。

- Supabase 在未来出现账号、跨设备收藏、投稿与审核等需求时才值得评估；现在接入会额外引入项目配置、权限和数据迁移。本文没有依赖任何 Supabase 的当前价格或具体 API 能力。
- SQLite 适合以后有单一服务端、较大索引或多维查询的情况；静态前端不能直接把服务器端 SQLite 当成可写数据库。几十到几百条 JSON 不需要它。
- 内容逐渐增加时，先观察文件编辑、构建体积和查询是否真正成为问题。更换存储应发生在内容读取接口后面，不让卡片组件知道数据库名称。

### 7.3 需要验证的边界

浏览器只请求同源静态资源，因而核心流程不依赖第三方 CORS。CORS 仍影响未来浏览器直连接口的可行性，不能由“本地脚本请求成功”推导出浏览器可调用。RSS 的抓取许可、摘要展示权和图片版权也不由 CORS 决定。

不代理外站、不执行外部 HTML、不接收用户任意抓取 URL，是这个架构自然带来的简化。第一版不增加外站截图、网页预览图抓取和复杂的链接自动修复。

## 9. UI / UX 初步方向

### 9.1 首页

首页像一个出发点：名称、标语、一个显眼的 Surprise Me 按钮、三个较轻的模式入口。说明短到不挡住第一次点击。首屏没有搜索框、内容排行榜、账户入口或仪表盘数字。

可用夜蓝背景、暖白文字和少量亮色指示，搭配简洁的旧浏览器边框或坐标标记。它应有一点未知感，但不能让用户猜不出哪里可以点击。V0.1 选定一种视觉隐喻即可，不同时制作地图、星图和漂流动画。

### 9.2 漫游与模式切换

- 当前模式保持可见；模式切换在一处完成，下一站按钮位置固定。
- 桌面保留足够留白，移动端优先保证标题、来源、打开与下一站无需寻找。
- 新结果出现用约 150～300ms 的轻微渐变或位移表达换站。数据已在本地，不人为等待几秒制造“正在搜索”的错觉。
- 支持键盘焦点、清晰的按钮文本和 `prefers-reduced-motion`；不强制播放声音。
- 结果上方可以出现轻量文案，如“下一站可能与你毫无关系”，但不能遮住真实来源和时间。

### 9.3 Time Machine 的年代感

第一版用内容与少量 CSS tokens 传递年代：1999 可以有方角、细边框和等宽标题；2007 可以有克制的渐变和浅色面板；2012 可沿用更简洁的基础样式。只做基础主题与少量年代覆盖，不开发三套布局，不复刻某家网站的完整界面。

时间卡明确区分：**当年事件、当年代表性去处、保存于某时的网页快照**。只有经过核实的日期才显示为具体日期。用“2007：这一年的几个入口”代替“今天的互联网”，不把编辑挑选的站点称为未经证实的热门排名。

历史主题只改变漫游器外观。进入 Wayback 后用户看到的视觉、链接去向和完整程度由外部档案决定，漫游器不承诺其子链接始终停留在选中年份。

### 9.4 第一版值得做与应推迟的视觉工作

值得做：统一内容卡、清晰来源、快速换站、简短年代背景、三卡年份包、小型最近遇见抽屉、手机布局。应推迟：三维星图、可拖拽网络地图、长过场动画、完整旧浏览器桌面、逐年份定制皮肤和截图墙。

## 10. 第一阶段开发路线与验收

先建立“静态内容即可玩的循环”，再接新闻。以下 9 项都可以单独完成并检查；时间估算包括实现、内容处理与基本验证，不假设数据已经准备好了。

| 顺序 | 任务 | 可检查的完成条件 | 估算 |
| --- | --- | --- | --- |
| 1 | 最小 Vite / React 框架与三视图 | 本地可启动；静态构建成功；带仓库子路径的路由可打开 | 0.25～0.5 天 |
| 2 | WanderItem、配置与数据校验 | 无效 URL、重复 ID、新闻缺日期、档案缺时间被阻止；先用少量真实条目跑通 | 0.5 天 |
| 3 | 筛选首批网站与年份包 | 至少 30 个现代网站、3 年 × 6 条内容；每条有来源；快照实际检查，记录待修项 | 1～1.5 天 |
| 4 | 统一卡片、Elsewhere 与最近遇见 | 打开、上一站、下一站可用；刷新恢复；存储失败不影响漫游 | 0.5 天 |
| 5 | Time Machine | 只展示有内容的年份；三卡包与换年可用；年代与抓取时间不会混淆 | 0.5～0.75 天 |
| 6 | Surprise Me 与选择器边界 | 三池选择、去重、单条池和空池处理通过；不因池耗尽无限循环 | 0.25～0.5 天 |
| 7 | RSS adapter 与 News Drift | 核实来源条件；归一化与去重；单源失败保留旧数据；时效状态正确 | 0.5～0.75 天 |
| 8 | 发布与周期更新 | 一份工作流能手动及定时更新并发布；失败保留可用站点；公开链接可打开 | 0.25～0.5 天 |
| 9 | 连续体验与最终收敛 | 手机／桌面核心流程；20 次漫游；来源过期、快照失效、无本机存储场景；删除拖慢体验的设计 | 0.25～0.5 天 |

实施顺序按依赖推进，内容准备可以穿插进行。遇到时间不足，先削减视觉、种子数量增长目标和来源数量；保持三页结构、统一模型和时间语义。不要通过加入第二个新闻 API 来补救第一个来源的接入阻塞。

### 必要的测试，不堆测试数量

- **模型与采集：**固定 feed 样本覆盖缺日期、同一文章重复、异常链接和单源失败，确认旧快照不会被空结果覆盖；合法的空 feed 也不能被永远当作“失败”保留旧闻，旧条目仍按 7 天规则退出。
- **选择器：**注入可控随机函数与时钟，验证硬过滤、去重放宽顺序、空池、单条池与按媒体／年份分组选择；不做容易波动的“大量随机抽样必须精确等比”测试。
- **时间：**验证 48 小时来源新鲜度和 7 天文章有效期，及不同日期字段的显示；在发布不再更新时浏览器仍能正确使新闻过期。
- **核心体验：**一个浏览器冒烟流程覆盖 Home → Surprise → 外链点击 → 最近遇见 → Time Machine；另手动确认移动端、外部标签页和减少动画设置。

### 发布验收闸口

完整 V0.1 应同时具备可玩的三个模式、第四个统一入口、来源标识和失败降级。尚未完成内容审核或 News Drift 未接通时可以发布受限预览，但 README 与页面必须如实说明，不能把这算作全部完成。

## 11. 未来 1～2 年的可维护性

### 11.1 稳定层、数据源层、实验层

| 层 | 应稳定的内容 | 可以怎么扩展 |
| --- | --- | --- |
| 核心稳定层 | ID 与类型语义、时间字段、模式约束、选择器输入输出、内容读取接口 | 添加兼容字段，新增模式定义与局部规则 |
| 外部数据源适配层 | 接收一条来源配置，输出归一化条目及来源状态；提供错误边界 | 新增一个 adapter 文件，将第三方字段在此映射，不侵入 UI |
| 数据与配置层 | 人工内容、来源政策、支持年份、随机权重 | 增加 JSON 数据和配置，校验通过后发布 |
| 可实验层 | 文案、动画、卡片布局、年代 CSS tokens | 可以频繁替换，不改动新闻采集和模型语义 |

不先实现插件市场、动态模块加载或通用 Provider SDK。V0.1 的“可替换”只需要一个明确的 adapter 函数约定和一个小注册表：来源配置选择 adapter，adapter 输出 WanderItem；页面不认识 RSS、GDELT 或 Wayback 的原始响应。

### 11.2 最少维护约定

1. **一份模型定义、一套校验。**人工数据、RSS 输出与前端读取共用规则；遇到不合法条目给出来源与 ID，不让坏数据直接进入界面。
2. **内容也有版本。**人工编辑通过 Git diff 检查；新闻快照独立文件，避免混进人工历史内容。数据源变动只调整配置或 adapter。
3. **保存依赖锁文件。**开发工具和 parser 不无计划追新；集中检查依赖更新，发现实际问题再修复。
4. **文档短而有边界。**README 写启动、更新数据、发布；核心模块写输入与职责；ROADMAP 只记录下一步与明确推迟项；CHANGELOG 记录用户可见变化和模型变更。
5. **少量监控先用现有工具。**看 Actions 结果和页面的最后更新时间；不搭建监控平台。维护者定期确认定时任务仍启用。
6. **内容维护形成小习惯。**建议每周花约 20～30 分钟补充或替换几条内容，复查问题链接与新闻来源；每月抽查年份包和档案链接。工作量超出预期时减少来源与数量目标。
7. **承认外部链接会变化。**区分临时超时、403、确认失效；将来增加健康检查时也不自动永久删除。默认先禁用，保留可追溯记录。

### 11.3 什么情况下才升级架构

- 需要登录、跨设备收藏、多作者同时维护或公开投稿时，再比较 Supabase 等托管后端。
- 构建周期无法满足真实时效需求，或必须在运行时使用带密钥的 API 时，增加一个薄的服务端入口及缓存；UI 仍读统一模型。
- JSON 的规模确实拖慢构建、下载或编辑时，先按内容类型／年份拆分加载，再决定是否需要数据库。
- 只有积累了用户对“熟悉／陌生”的明确反馈，才讨论 Discovery Distance；不能把国家差异、语言差异或冷门程度直接当成用户兴趣距离。

这一方案的持续维护能力来自清楚的职责、稳定的数据语义和可替换的数据入口，不来自提前搭建基础设施。未来是否换框架不应迫使重新整理全部内容。

## Recommended V0.1

如果现在开始写代码，建议最终只包含以下内容：

1. **一个简单主页：**Surprise Me 最突出，旁边是 Elsewhere、News Drift、Time Machine。
2. **Elsewhere：**至少 30 个审核过的网站、一句话介绍、打开与下一站。
3. **Time Machine：**3 个精选年份、每年约 6 条内容；可选择／随机年份，每次出现三张带上下文的卡片；只做轻量年代样式。
4. **News Drift：**少量合规可用 RSS 的近 7 天标题、媒体、原文语言、发表时间与原文链接；来源允许时才显示摘要；目标 3～5 个来源、每 12 小时更新静态快照。
5. **Surprise Me：**从可用的网站、新闻、历史池中分组随机，最近 20 条去重，小池耗尽后仍可继续。
6. **本机最近遇见与基础容错：**能找回刚才的内容；来源失败、新闻过期、档案打不开时都有下一步。
7. **一个可分享的静态网址与必要说明：**React + Vite + TypeScript、JSON、一个 RSS 采集脚本与发布工作流。

**明确推迟：**任意日期的历史新闻、任意年份自动生成、完整历史互联网模拟、全文采集与转载、精准陌生度推荐、复杂分类筛选、账号和云收藏、社区投稿、CMS、数据库、重型视觉系统。

最先值得验证的，是用户看完一个意外发现后，是否还想再点一次“下一站”。
