> **实施补记（2026-10-02）：**以下正文保留最初规划时的核实状态。开发阶段已实际核查首批 30 个网站、18 条历史内容及 3 个 RSS 来源；详细依据见 [内容核验记录](docs/CONTENT_AUDIT.md) 与 [新闻来源说明](docs/NEWS_SOURCES.md)。其他候选服务的额度、价格与使用条件仍未核实。

**第一版的数据组合：人工精选网站 + 少量公开 RSS 的静态快照 + 人工整理的年份包 + 选定的 Wayback／Internet Archive 外链。** 不将任何在线第三方 API 放进用户点击“下一站”的关键路径。

## 1. 核实状态与阅读方式

本轮尝试联网读取官方资料，但两次请求均被中断，**没有成功验证下述网页内容、API 响应、当前价格、额度或 feed 可用性**。以下比较基于各类服务的基本用途与已知接入模式；列出的官方入口用于后续接入核实，不代表已经完成实时调查。

因此：

- 不给出未经核实的“每天免费 X 次”或保证有效的免费套餐。
- 区分“公开可访问”“不需要 Key”“允许公开部署”“允许展示摘要／全文”四件事。
- 历史数据覆盖和 CORS 均按具体接口、具体部署方式验证，不能由平台名称推断。
- 推荐架构刻意不依赖复杂 API 的当前配额，资料复核失败时仍可先完成网站与历史漫游。

## 2. 现代网站：优先人工策展

| 候选发现途径 | 能带来的内容 | 获取方式与维护成本 | V0.1 决策 |
| --- | --- | --- | --- |
| 个人网站、博客的 blogroll、友情链接、webring | 独立作者与非平台化网络 | 人工点开、沿链接发现；可能失效，但很贴合项目精神 | 主来源；自己写简短介绍 |
| 小型独立网站目录、数字艺术集合、趣味站点集合 | 密度较高的候选链接 | 作为线索，逐个访问；目录数据的复制权与链接本身不是一回事 | 不整库搬运，不默认它们持续准确 |
| 大学／实验室／博物馆／个人项目页面 | 冷门知识、实验、旧页面 | 人工筛选；官方性质不保证页面有趣或持续在线 | 用于扩大内容类型 |
| GitHub 公开列表与 README | 技术、艺术与网络文化候选 | 检查仓库许可及来源；列表可能偏开发者圈层 | 只作发现渠道，保留必要署名与依据 |
| 自己仓库的 JSON | 已审核、可版本化的内容 | 最透明、无第三方运行时依赖 | 作为应用的实际内容源 |

`data/sites.json` 的初始 30 条建议覆盖个人主页／博客、艺术／实验、小工具／个人项目、知识／实验室、小型档案／社区等至少 5 类。先保证类型差异；不要为了“陌生”而追求危险链接或刻意晦涩的内容。

每条至少确认：不用账号即可理解主要内容，链接可访问，有明确可说明的看点，不强迫下载，不含明显欺骗性跳转。检查标准保持简短；不把它做成内容审核平台。

元数据由自己维护，不抓取目标网站全文、截图或封面图。描述优先原创；如果借用目录的文案或数据结构化成果，需要遵守其许可。链接被收录不意味着外站未来的所有内容都得到本项目认可。

## 3. 新闻来源比较

下表的费用／Key 描述是接入模式判断，**不是当前套餐核验结果**。实施前逐源确认；尤其不要因为“个人项目”就把公开网址当作本地开发环境。

| 来源 | 费用／Key 与限制 | 历史支持与内容特点 | CORS／展示条件 | 适合程度 |
| --- | --- | --- | --- | --- |
| **媒体官方 RSS / Atom** | 很多 feed 公开且无 Key；频率和再展示条件由媒体规定，没有统一免费额度 | 通常只有近期有限条目；结构、日期、摘要完整度不一致 | CORS 各异；RSS 中有全文也不等于可转载全文 | **首选**：3～5 个源，构建环境采集 |
| **公共机构／科研机构的 RSS** | 常见公开入口，需逐个检查限制与许可 | 有助于跳出综合时政；通常不应被称为当地媒体或独立新闻报道 | 机构内容、第三方图片与素材可能适用不同许可 | 可作为明确标注的主题资讯来源，不能冒充媒体覆盖 |
| **GDELT** | 公开数据／API 是候选；具体接口、请求限制与服务可用性待核实 | 擅长大范围新闻发现和结构化研究；不同数据集的历史跨度与查询窗口不同 | 不能由索引或摘要获得原文转载权；浏览器策略逐接口确认 | V0.2 以后做补充 adapter，不做首版必需依赖 |
| **Media Cloud** | 研究工具与 API 访问可能涉及账户、Key 和配额，当前资格待核实 | 面向媒体研究、来源集合和报道检索；覆盖依来源与具体产品而定 | 研究访问不自动等于可再发布全文；CORS 不能预设 | 暂缓，接入与概念成本偏高 |
| **NewsAPI 等商业聚合 API** | 通常需要 Key，免费开发套餐与公开使用权需区分；现价／限额待核实 | 历史窗口、来源和延迟常受套餐限制；返回元数据不等于完整文章 | Key 应留在采集环境；全文与图片权利通常不随 API 返回自动转让 | 不作为零付费 MVP 的基础 |
| **The Guardian Open Platform** | 有独立的开发者接入与使用条件；当前 Key、额度及公开项目资格待核实 | 单一媒体，可能提供丰富档案，但不能构成“陌生国家新闻”的整体覆盖 | 各字段的使用、署名和缓存要求需看条款 | 可作为后续单源实验，不独自承担 News Drift |
| **Google News RSS** | 常能遇到 RSS 形式的聚合链接，但不能假定是有稳定支持与承诺的通用公共 API | 适合发现近期报道；地区／语言查询行为、重定向和历史可得性不稳定 | 不应靠解析包装链接绕过访问限制；原文版权仍归原媒体 | 不作 V0.1 核心依赖 |
| **Wikimedia / Wikipedia** | 公开读取接口、认证和流量政策按具体服务确认 | 历史事件与背景知识有用，不是普遍意义的实时新闻聚合 API | 正文、结构化数据和媒体文件许可不同，须正确署名 | 用于历史资料核对；不是 News Drift 主源 |

### 3.1 为什么 RSS 在这个阶段最合适

RSS 提供的是出版方主动给出的结构化入口。项目只需要标题、原文链接、来源、时间，因而不必抓原网页 DOM，也不必建立文章抽取器。少量源的解析、失败隔离和定时刷新可以限制在一个脚本中。

限制同样明确：有些 feed 没有许可摘要再展示；有些只返回最近十几条；有些日期或编码不可靠；有些网站停止维护 RSS。解决方式是换一个源、减少字段或禁用，而不是立刻接上复杂爬虫。

### 3.2 候选来源如何挑选

先从官方 RSS 索引寻找实际 feed，候选类型可以是国际／地区媒体、较小的本地媒体与科学／文化机构。不要只挑 BBC、DW 等国际媒体就宣称看到了各地社区的本地报道；它们只能代表自己发布的内容。

可供实施时查找的官方入口包括 [BBC RSS 说明](https://www.bbc.co.uk/news/10628494)、[DW](https://www.dw.com/)、[NHK WORLD-JAPAN](https://www3.nhk.or.jp/nhkworld/)、[NASA](https://www.nasa.gov/)。**这些是候选检索入口，未确认当前 feed 地址、可达性或使用许可，不是已经选定的上线清单。** 其中 NASA 应标为机构资讯，而非新闻媒体。

接入第一条后再接第二条，避免先搜索几十个来源。发布目标是 3～5 个条件合适的来源，并尽量有 3 个媒体地区或明显不同的议题视角。原文语言可以相同，不为了形式上的多语言引入翻译服务；显示覆盖事实即可。

### 3.3 每个来源的最小核验记录

在 `config/sources.json` 中记录：

| 信息 | 核实内容 |
| --- | --- |
| `id` / `name` / `kind` | 稳定 ID、可展示名称、媒体或机构等真实属性 |
| `url` / `feedUrl` | 来源主页与官方公布的 feed；重定向后仍属于可信来源 |
| `publisherCountry` / `language` | 出版媒体所在地区与输出语言；不冒充报道事件所在地 |
| `displayPolicy` | 项目采用的展示方式：允许的标题与链接／允许摘要等；它是核实后的项目决策，不是平台提供的万能许可证 |
| `termsUrl` / `checkedAt` | 官方使用说明及人工核实日期；未核实则不填假日期 |
| `enabled` | 只有访问和展示条件都通过时才启用 |

检查一小批实际条目能否稳定提供标题、规范链接与发表时间；确认任何请求限制、署名要求、缓存和删除要求。CORS 仅在计划让浏览器直连时测试，本方案不需要为绕过 CORS 增加代理。

## 4. 历史新闻：先改变承诺，不硬凑自动化

历史内容必须区分三种来源：

1. **当年的原始报道：**可说明“当时的人正在读什么”，但获取与使用条件最不统一。
2. **当时网页的存档快照：**能呈现当时保存下来的页面，不保证当日新闻完整，也不保证全部链接在同一天。
3. **后来整理的历史回顾：**适合解释背景，不能伪装成当年的报道。

| 方案 | 适合做什么 | 主要障碍 | V0.1 决定 |
| --- | --- | --- | --- |
| 媒体自己的历史档案／API | 选定媒体或事件的原始报道 | 付费墙、Key、权限、缺失与不同许可 | 有清楚公开来源时手工收录链接，不做统一检索 |
| 图书馆、报纸数字化馆藏，例如 Library of Congress | 某地区、某时期的报纸与历史材料 | 馆藏覆盖不等于全世界；OCR、日期与权利状态需逐条核对 | 后续做一个有限专题，首版不接聚合 API |
| Wikimedia “历史上的今天”及相关条目 | 找事件线索与参考资料 | 返回纪念性事件不是当天新闻；内容质量与引用需核实 | 人工核对资料，不用“历史上的今天”替代历史报纸 |
| GDELT / Media Cloud 等索引 | 在其实际覆盖窗口内找到报道 | 当前查询接口的回溯窗口可能小于底层数据跨度；不保证原网页仍在线 | 暂缓，先验证具体查询与结果再立项 |
| 手工历史事件 JSON | 极少量有来源的年份包 | 需要编辑投入，但可控制准确性与体验 | **V0.1 推荐** |

首版用“当年发生了什么”“当年有哪些去处”替代“重现当天新闻”。每条事件写一小段原创说明并链接原始或可信参考资料；能找到当年报道则明确标注，只有后来回顾就显示“回顾资料”。

## 5. 旧互联网、Wayback 与 Internet Archive

### 5.1 两种入口不要混淆

- **Wayback Machine：**访问某个 URL 在特定抓取时间的网页快照。适合旧网站和网页外观。
- **Internet Archive 馆藏页：**访问书籍、软件、音频、视频等馆藏条目及其元数据。适合互联网文化材料；许可、访问方式和可用性由具体条目决定。

存档平台提供访问，不代表自动授予转载或镜像所有内容的权利。V0.1 优先外链跳转，不把整个旧站或馆藏下载后重新托管。

### 5.2 API 的角色

| 能力 | 可解决的问题 | 不应做出的承诺 |
| --- | --- | --- |
| Wayback Availability API | 为一个已知 URL 寻找可用／接近目标时间的快照候选 | 返回最近候选不等于选中年份一定存在，也不保证页面完整 |
| Wayback CDX | 查询捕获索引及时间戳，辅助挑选候选 | 索引存在不等于当前一定能打开；不能当作所有历史内容的语义搜索 |
| Internet Archive 元数据接口 | 获取某个馆藏条目的元数据与文件信息 | 元数据可读不等于文件可自由传播或可在本站直接播放 |

这些接口有公开的文档与常见读取用法，但本轮未核实当前认证、流量限制和可用性。第一版不调用它们也能实现：维护者用浏览器检查快照，把**实际可打开的最终快照地址与真实时间戳**放入数据文件。

### 5.3 快照收录步骤

1. 选择一个和年份有关的网站，记录为何值得看，而不只是“它很老”。
2. 找到该年份的快照，打开确认正文与主要视觉是否可理解。
3. 检查最终页面显示的抓取时间；发生重定向时重新确认，不只看请求 URL 里的时间。
4. 记录原网址、实际快照地址、实际 `capturedAt` 与 `history.year`。
5. 同年没有可用快照就换条目；首版不自动选择别的年份冒充。若未来允许跨年候选，必须另行设计明确的时间偏差提示。
6. 为卡片写一句背景说明，注明哪些元素缺失；严重损坏或强依赖登录的快照不进入首批池。

一个 2009 年快照可能包含 2007 年文章，但它依然是 2009 年保存的页面。事件年份、发表时间、快照时间分别表达，不能任选一个塞进统一的 `date` 字段。

## 6. 数据管线、时效与版权边界

### 6.1 最小运行方式

人工内容走“编辑 JSON → 校验 → 构建”；新闻走“定时采集白名单 feed → 归一化 → 与最近成功快照合并 → 校验 → 构建”。两条管线最终都输出 WanderItem，页面不需要知道某条新闻来自哪种 API。

新闻计划每 12 小时检查一次，每源最多保留 15 条近 7 天内容；这是项目自己的产品规则，不是来源方配额。请求频率还要服从来源条款。来源超过 48 小时未成功更新时退出 Surprise Me，News Drift 仅可带明确旧快照提示展示仍未超过 7 天的条目。

构建成功并不证明每个来源刚刚刷新成功。保存每源 `lastSuccessAt`；UI 直接读取这一字段。相同 GUID／规范化 URL 的条目合并；URL 清理只去掉明确的跟踪参数，不随意删除可能影响正文定位的查询参数。

同一标题不能作为唯一去重键，不同媒体可能用同名标题报道不同事情。首版按原文地址做确定性去重，不承诺识别转载链或跨语言的同一事件。

### 6.2 展示什么

默认显示来源允许展示的标题、媒体、发表时间和原文链接；简短摘要必须有适用许可或由维护者原创。图片、付费内容和全文转载全部不进入 V0.1。

“只显示标题和链接”是减少依赖的产品策略，不能被当成所有来源都自动适用的法律许可。接入时仍看来源条款；RSS 公开、API 返回全文、Wayback 能打开，分别只是访问事实。

使用 Wikimedia 材料时应检查所用内容的具体许可，保留必要署名和许可链接；不能把 Wikipedia 文本、Wikidata 数据、Commons 图片视为同一种许可。V0.1 优先自行概述事实并链接参考资料，不批量复制百科段落。

## 8. 开始实施时的短清单

1. 先人工选 5 个网站与一个小年份包，确认“打开 → 返回 → 下一站”真的有趣，再补足发布内容。
2. 找到第一条官方 RSS，核实公开展示条件，测试少量条目的字段；只有这条跑通后才扩到 3～5 个来源。
3. 对每个拟上线来源记录条款链接与真实核实日期；任何未确认的条件保留为待办，不写成已经通过。
4. 人工打开每张首批历史快照，确认实际抓取年份与内容完整度；不只测 HTTP 状态码。
5. 演练一个来源失败、所有新闻过期、一个档案链接失效，确认仍能继续漫游。
6. 复核托管与定时任务规则，跑一次手动更新和一次公开部署；核心依赖与内容条件没通过时，按受限预览标示。

**后续才考虑自动化扩大覆盖。** 第一版真正稀缺的是值得偶遇的内容与可靠的时间语境，不是可以调用的 API 数量。
